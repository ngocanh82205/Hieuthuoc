# 2.3. Thiết kế kiến trúc hệ thống

## 2.3.1. Kiến trúc tổng thể

*[Hình 2.x. Sơ đồ kiến trúc tổng thể – trang "Kiến trúc tổng thể" trong `docs/drawio/kien-truc-he-thong.drawio`]*

### Các thành phần của hệ thống

| Thành phần | Công nghệ | Trách nhiệm |
|---|---|---|
| Trình duyệt web (giao diện web) | HTML, Bootstrap 5, Bootstrap Icons, JavaScript, Chart.js | Hiển thị giao diện cho khách hàng, dược sĩ / nhân viên, quản trị viên. Gửi form. Dùng `fetch` cho các chức năng cần cập nhật mà không tải lại trang: chat tư vấn, đếm thông báo, phí giao hàng, chọn tỉnh / quận / phường |
| Ứng dụng client (VinaPharma App) | SPA: HTML, Bootstrap 5, JavaScript (Fetch API) | Ứng dụng một trang chạy trên trình duyệt / điện thoại, chỉ giao tiếp với hệ thống qua REST API `/api/v1` bằng Bearer token (mục 2.6) |
| Ứng dụng máy chủ | Spring Boot 3.5 (Java 17), Spring MVC, Thymeleaf, Spring Security, Spring Data JPA / Hibernate, Tomcat nhúng | Xử lý toàn bộ yêu cầu: định tuyến, xác thực và phân quyền, xử lý đơn hàng, kho, thanh toán, tư vấn. Dựng trang HTML cho giao diện web và cung cấp REST API JSON (`/api/v1`) cho ứng dụng client. Phục vụ file tĩnh (CSS, JS) |
| Bộ lập lịch | Spring Scheduling (`@EnableScheduling`, `@Scheduled`), chạy trong cùng tiến trình | Mỗi 15 phút (`OrderMaintenanceScheduler`): tự hủy đơn bỏ ngang để nhả hàng đang giữ chỗ - đơn bị từ chối đơn thuốc mà khách không tải lại, đơn thanh toán online chưa trả tiền, báo giá chưa được khách xác nhận |
| Cơ sở dữ liệu | MySQL 8 / MariaDB (XAMPP), CSDL `Hieuthuoc`, InnoDB, utf8mb4 | Lưu trữ toàn bộ dữ liệu nghiệp vụ (37 bảng, mục 2.4) |
| Lưu trữ file | Hệ thống file của máy chủ | Vùng công khai: ảnh sản phẩm, bài viết. Vùng riêng tư: ảnh đơn thuốc, ảnh chat; chỉ chủ sở hữu và nhân viên có quyền xem được qua `FileController` |
| Dịch vụ bên ngoài | PayOS, VNPay, VietQR, GHN, Claude / Gemini, SMTP, OpenStreetMap Nominatim | Thanh toán online, mã QR chuyển khoản, tính phí và tạo vận đơn, trợ lý AI, gửi email, tra cứu địa chỉ |

### Backend và client có triển khai độc lập không?

Hệ thống có hai loại client, triển khai theo hai cách khác nhau:

- **Giao diện web** (khách hàng, nhân viên, quản trị) dựng ở máy chủ (server-side rendering) bằng template Thymeleaf. Giao diện nằm cùng mã nguồn và cùng tiến trình với phần nghiệp vụ, trình duyệt nhận HTML đã dựng sẵn.
- **Ứng dụng client VinaPharma App** là client độc lập về mặt logic: chỉ dùng REST API, không phụ thuộc template hay phiên đăng nhập của máy chủ. Hiện ứng dụng được phục vụ như file tĩnh tại `/app`; có thể đưa sang máy chủ / CDN khác hoặc thay bằng ứng dụng di động mà không phải sửa backend (API đã bật CORS).

Phần backend, gồm Tomcat nhúng, REST API, file tĩnh và bộ lập lịch, đóng gói chung thành **một file `.jar`** (kiến trúc nguyên khối - monolith). Lựa chọn này phù hợp quy mô một nhà thuốc:
- triển khai đơn giản;
- chỉ một nơi kiểm tra quy tắc nghiệp vụ: giao diện web và REST API cùng gọi chung tầng Service;
- API có phiên bản (`/api/v1`), nên client cũ không bị ảnh hưởng khi backend nâng cấp.

### Client giao tiếp với backend bằng giao thức nào?

**HTTP / HTTPS là giao thức chính.**
- Trình duyệt gửi `GET` để xem trang, `POST` để gửi form. Máy chủ trả về trang HTML.
- Mọi form `POST` đều kèm mã CSRF. Sau khi xử lý `POST`, máy chủ chuyển hướng (mẫu Post/Redirect/Get) để tránh gửi lại form khi người dùng tải lại trang.
- Upload ảnh dùng `multipart/form-data`, giới hạn 5MB mỗi file.

**Cập nhật một phần trang.** Với chat tư vấn, đếm thông báo chưa đọc và phí giao hàng, JavaScript gọi `fetch` tới các đường dẫn trả JSON để cập nhật một phần trang. Chat lấy tin nhắn mới bằng cách hỏi định kỳ (polling).

**REST API cho ứng dụng client.** Client gọi `/api/v1/**` bằng HTTP với dữ liệu JSON (riêng tải ảnh dùng `multipart/form-data`). API dùng đúng phương thức HTTP (`GET`, `POST`, `PUT`, `DELETE`) và mã trạng thái (200, 201, 401, 403, 404, 409, 422...). Đặc tả chi tiết ở mục 2.5.

**Xác thực.** Có hai chuỗi bảo mật tách riêng:
- Giao diện web dùng phiên đăng nhập (session) và cookie `JSESSIONID` (`HttpOnly`, `SameSite=Lax`), kèm chống CSRF.
- REST API phi trạng thái: client đăng nhập qua `POST /api/v1/auth/login`, nhận access token JWT (ký HMAC-SHA256, hạn 24 giờ), rồi gửi kèm header `Authorization: Bearer <token>`. API không dùng cookie nên không cần CSRF.

**Giao tiếp với dịch vụ bên ngoài** bằng HTTPS / REST (JSON):
- Ứng dụng chủ động gọi API của PayOS, GHN, Claude / Gemini, Nominatim. Với VNPay, ứng dụng chuyển hướng khách sang URL thanh toán có chữ ký.
- Theo chiều ngược lại, cổng thanh toán và GHN gọi về ứng dụng qua webhook / IPN để báo kết quả. Các đường dẫn này được miễn CSRF nhưng phải kiểm tra chữ ký HMAC.
- Khóa API chỉ nằm ở cấu hình máy chủ, không bao giờ gửi xuống trình duyệt.

### Backend truy cập dữ liệu như thế nào?

- Ứng dụng truy cập MySQL qua **JPA / Hibernate**. Bên dưới là JDBC (MySQL Connector/J) với pool kết nối HikariCP. Controller không viết SQL.
- Thao tác thường dùng **Repository** của Spring Data JPA. Các phép thống kê (tồn kho, doanh thu, giá vốn) dùng SQL tổng hợp qua lớp `Sql`, để CSDL tự tính.
- Các thao tác nghiệp vụ nhiều bước (đặt hàng, duyệt đơn thuốc, xuất kho, hoàn tiền) chạy trong **giao dịch CSDL** (`@Transactional`) và **khóa dòng** (`LockModeType.PESSIMISTIC_WRITE`, tương đương `SELECT ... FOR UPDATE`). Nhờ đó, hai người thao tác cùng lúc không làm lệch tồn kho hay duyệt trùng.
- **Cấu trúc bảng** sinh từ các Entity JPA: Hibernate (`ddl-auto=update`) tạo các bảng / cột còn thiếu khi khởi động. Dữ liệu mẫu được tạo bằng `DataSeeder` khi CSDL trống.
- **File tải lên** được lưu qua `FileStorageService`, có kiểm tra loại file, dung lượng và chặn path traversal. CSDL chỉ lưu tên file.

## 2.3.2. Kiến trúc phân tầng của ứng dụng

*[Hình 2.y. Sơ đồ kiến trúc phân tầng – trang "Kiến trúc phân tầng backend"]*

Ứng dụng tổ chức theo mô hình **MVC**, mở rộng thêm tầng **Service** và tầng **Repository**. Một yêu cầu đi lần lượt qua các bước sau:

**Bộ lọc bảo mật & Interceptor → Controller (web) / REST Controller (API) → Service → Repository / Entity → CSDL**

Controller web trả view (HTML); REST Controller trả JSON qua DTO. Mỗi tầng chỉ gọi tầng ngay dưới nó.

| Tầng | Thành phần trong mã nguồn | Trách nhiệm |
|---|---|---|
| Giao diện (View) | `templates/` (Thymeleaf: `layouts`, `partials`, `shop`, `account`, `auth`, `consult`, `staff`, `admin`), `static/js/app.js`, `static/css`; ứng dụng client `static/app/` | Hiển thị dữ liệu controller truyền sang thành trang HTML. Định dạng tiền và ngày (bean `ViewHelper`). Hiển thị lỗi và thông báo. Tự escape dữ liệu để chống XSS. Không chứa logic nghiệp vụ |
| Bảo mật & Interceptor | `config/SecurityConfig` (web: session, CSRF), `api/ApiSecurityConfig` + `TokenService` (API: Bearer token), `StaffAccessInterceptor`, `WebConfig` | Chặn yêu cầu chưa đăng nhập hoặc sai vai trò (`/account/**`, `/staff/**`, `/admin/**`, `/api/v1/**`). Kiểm tra quyền chức năng chi tiết của nhân viên (`StaffPermission`: ORDER, RX_REVIEW, INVENTORY, POS...). Chống CSRF cho giao diện web. Băm mật khẩu BCrypt. Ghi nhận nhân viên đang trực tuyến |
| Điều khiển (Controller) | `web/`: nhóm cửa hàng (`ShopController`, `CartController`, `AccountController`, `ConsultController`, `PaymentController`, `AuthController`, `FileController`...); `web/staff/` (`StaffController`, `OrderController`, `PosController`, `ConsultationController`, `ContentController`, `InventoryController`); `web/admin/` (`DashboardController`, `ReportController`, `FinanceController`, `UserController`, `CatalogController`, `MarketingController`, `StockController`, `SystemController`...); `api/` (REST: `AuthApi`, `CatalogApi`, `ShoppingApi`, `AccountApi`, `ConsultApi`, `StaffApi`, `AdminApi`, kèm `Dto`, `ApiExceptionHandler`) | Nhận dữ liệu từ yêu cầu, kiểm tra định dạng đầu vào. Gọi service tương ứng. Trả view, hoặc JSON theo định dạng chuẩn. Chuyển hướng kèm thông báo (`Flash`). Controller mỏng, không tự xử lý quy tắc nghiệp vụ |
| Nghiệp vụ (Service) | `service/`: `OrderService`, `CartService`, `PaymentService`, `PosService`, `InventoryService`, `StockService`, `SafetyService`, `ChatService`, `AiAssistantService`, `PromotionService`, `VoucherService`, `ProductAdminService`, `ReportService`, `NotificationService`... | Nơi duy nhất cài đặt quy tắc nghiệp vụ: chuyển trạng thái đơn; giữ chỗ và xuất kho FEFO; duyệt đơn thuốc; tính khuyến mãi, điểm, phí giao; kiểm tra an toàn thuốc; quy tắc chuyển cho dược sĩ. Quản lý giao dịch CSDL, ghi nhật ký thao tác, gửi thông báo. Dùng chung cho giao diện web và REST API |
| Truy cập dữ liệu (Repository) | `repository/` (Spring Data JPA: `UserRepository`, `ProductRepository`, `SettingRepository`...), `EntityManager` (JPQL), lớp `Sql` | Thực hiện CRUD và truy vấn theo điều kiện (JPQL). Thực hiện truy vấn tổng hợp bằng SQL. Khóa dòng khi tầng Service yêu cầu |
| Miền (Entity) | `entity/` (JPA: `User`, `Order`, `OrderItem`, `Prescription`, `Product`, `Batch`, `Receipt`...), enum (`OrderStatus`, `DrugType`, `PaymentMethod`, `MemberTier`, `StaffPermission`...) | Ánh xạ bảng CSDL thành đối tượng. Khai báo quan hệ giữa các bảng. Cung cấp các phương thức tính toán đơn giản trên một đối tượng. Enum gói các quy tắc cố định, VD: trình tự trạng thái đơn hợp lệ, loại thuốc bắt buộc có đơn |
| Cơ sở dữ liệu | MySQL 8 (37 bảng) | Lưu trữ bền vững. Bảo đảm ràng buộc khóa chính, khóa ngoại, khóa duy nhất |

Ngoài các tầng chính, có hai nhóm thành phần dùng chung.

**Tích hợp bên ngoài**
- Gồm: `PaymentService` (PayOS, VNPay, VietQR), `GhnService` (kèm Nominatim), `ClaudeClient` / `GeminiClient`, `MailService`, `FileStorageService`.
- Các lớp này đóng gói lời gọi API bên ngoài, để tầng Service dùng như một hàm bình thường.
- Khi chưa cấu hình khóa API, chúng chuyển sang chế độ thay thế: trang thanh toán thử, phí ship cố định, trợ lý AI trả lời theo kịch bản.
- `AiAssistantService` gọi AI trên một nhóm luồng riêng, để khách không phải chờ.

**Xử lý chung**
- `BusinessException` là lỗi nghiệp vụ do tầng Service ném ra (kèm mã HTTP). Với giao diện web, `GlobalControllerAdvice` bắt lỗi, chuyển về form cũ, giữ dữ liệu đã nhập và hiện thông báo; trang lỗi 403 / 404 / 500 cũng xử lý tại đây. Với REST API, `ApiExceptionHandler` chuyển lỗi thành JSON `{success: false, message, errors}` với mã 400 / 404 / 409 / 422...
- `SettingService` đọc các tham số nghiệp vụ cấu hình được: thời hạn đơn thuốc, phí ship, điểm tích lũy...
- Bảng `audit_logs` ghi nhật ký thao tác.

### Ví dụ luồng xử lý "Dược sĩ xác nhận đơn hàng"

1. Trình duyệt gửi `POST /staff/orders/{id}/status` kèm trạng thái mới và mã CSRF.
2. Spring Security kiểm tra người dùng đã đăng nhập và có vai trò Dược sĩ hoặc Quản trị viên. `StaffAccessInterceptor` kiểm tra quyền `ORDER`.
3. `staff/OrderController.changeStatus()` gọi `OrderService.changeStatus()`. (Ứng dụng client gọi `POST /api/v1/staff/orders/{id}/status` kèm Bearer token; `StaffApi` gọi cùng phương thức service.)
4. `OrderService` mở giao dịch và khóa dòng đơn hàng. Sau đó kiểm tra trình tự trạng thái hợp lệ (`OrderStatus`), tình trạng thanh toán và cảnh báo an toàn thuốc. Cuối cùng cập nhật entity `Order` và ghi `OrderHistory`.
5. Service gửi thông báo cho khách và ghi nhật ký thao tác.
6. Controller chuyển hướng về trang chi tiết đơn kèm thông báo thành công. Nếu vi phạm quy tắc, `BusinessException` đưa dược sĩ về lại trang với nội dung lỗi; giao dịch tự hoàn tác.

## 2.3.3. Triển khai

- Ứng dụng được build bằng Maven (`mvnw package`) thành một file `.jar` chứa sẵn Tomcat nhúng. Máy chủ chỉ cần cài JDK 17 trở lên.
- **Khi phát triển:**
  - MySQL chạy bằng XAMPP (CSDL `Hieuthuoc` tự tạo nhờ `createDatabaseIfNotExist=true`, bảng do Hibernate sinh).
  - Ứng dụng chạy bằng `mvnw spring-boot:run`, cổng mặc định 8080 (đổi được qua biến môi trường `PORT`). Giao diện web tại `/`, ứng dụng client tại `/app`, REST API tại `/api/v1`.
  - Trang `index.php` trong thư mục XAMPP tự chuyển hướng sang `http://localhost:8080` khi ứng dụng đang chạy.
- **Khi triển khai thật:** chạy `java -jar` trên máy chủ. Chuỗi kết nối CSDL, thư mục lưu file và khóa API (PayOS, VNPay, GHN, `GEMINI_API_KEY`...) và khóa ký token `API_SECRET` đặt trong `application.properties` hoặc biến môi trường. Thư mục lưu file phải nằm trên ổ đĩa bền vững để không mất ảnh khi cập nhật phiên bản.
